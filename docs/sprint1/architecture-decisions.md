# 三项非功能需求的架构选择及理由

> CS5351 Assignment 2 要求对现有 smart-education-ideology 平台完成三项非功能需求改进。
> 本文档记录各需求的方案选型与理由，对应任务分配书（2026-09-22）第一节分工。

## 一、性能（Performance）

### 选定方案：聚合下推到数据库（MySQL）

**问题**：教师 Dashboard 的 `DashboardService.buildActivityTrend()` 将最近 7 天全部活动事件（实测约 10 万行）以 `SELECT *` 拉回 JVM，再在 Java 内存中循环分组计数；`StudentActivityEventService.getReport` 的总学习时长同样用 MyBatis Wrapper 全量读取后求和。数据量越大，内存占用与响应时间线性恶化。

**候选方案对比**：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| Java 内存聚合（现状） | 逻辑直观 | 传输 10 万行、JVM 内存压力、耗时随数据量线性增长 | ❌ |
| 聚合下推 MySQL（`GROUP BY` / `SUM`） | 改动局部（仅单方法 + 单条 SQL）；传输行数与事件总量解耦（最多 7 行）；结果可由定向测试验证一致 | 依赖数据库函数，可移植性略降 | ✅ **选定** |
| 应用层缓存（Redis/本地缓存） | 命中时最快 | 引入新组件、缓存失效与一致性问题，超出"局部优化"范围 | ❌ 过重 |
| 物化视图 / 定时汇总表 | 查询极快 | 需要引入汇总表 + 同步机制，改动面大 | ❌ 过重 |

**理由**：任务书要求"只选一处可复现的高成本查询做局部优化"。聚合下推不引入新组件、不改对外接口（返回的 7 个 `{day, value}` 数据点结构完全一致），且可用**同一数据集前后实测**证明收益。

**验证证据**（issue #4、PR #6、`perf-measurement.md`）：

- 10 万行数据、20 次请求取平均：**3,213.2 ms → 72.4 ms（↓ 97.7%）**。
- 定向测试断言 SQL 含 `GROUP BY`、不再全量 `selectList`、返回结构不变；原有回归测试原样通过。

## 二、安全（Security）

### 选定方案：统一 JWT 认证 + ADMIN 角色校验（拦截器层实现）+ 上传文件头校验

**问题**：`/api/admin/**` 管理员接口未做统一的登录态与角色校验；上传入口只校验扩展名，可被伪装文件绕过。

**候选方案对比**（管理员接口保护）：

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 统一拦截器校验 JWT + ADMIN 角色 | 一次实现覆盖全部 `/api/admin/**`；便于集中测试三类请求（未登录/普通用户/管理员） | 需梳理接口路径白名单 | ✅ **选定** |
| 每个 Controller 方法逐一注解 | 粒度细 | 易遗漏、重复代码、难以统一回归测试 | ❌ |
| 引入 Spring Security 全家桶 | 功能完备 | 对既有自研登录体系改动过大，超出课程"局部改进"要求 | ❌ 过重 |

上传校验选定：大小上限 + **文件头（magic number）检查**，而非仅扩展名——扩展名可随意伪造，文件头校验成本极低且覆盖"伪装类型文件"攻击场景。

**理由**：安全改进在"统一入口 + 最小侵入"之间取平衡，所有改动可通过三类请求的接口测试（issue #9 验收标准）逐项验证。

## 三、可维护与扩展（Maintainability & Extensibility）

### 选定方案：小步重构 + 一键回归验证

**三个局部动作**：

1. **一键回归入口**（赵俊楠，issue #2）：`scripts/verify_project.ps1` 依次执行后端测试、前端 TypeScript 类型检查、生产构建，任一失败即返回非零码。**理由**：小步重构最大的风险是"改完不敢动"，先建回归网再动代码；一键执行降低验证成本，也是每次 PR 的可复核证据。
2. **服务层局部整理**（江润家）：只整理 `TeachingMaterialService` 草稿保存路径中一处明确的重复处理，保持外部行为不变。**理由**：限定单一路径，避免"顺手大改"引入回归。
3. **前端组件拆分**（李洋，issue #7/PR #8）：仅从 `KnowledgeGraph.tsx` 提取现有 `KnowledgeRelationList` 组件，筛选逻辑与状态仍由父组件管理。**理由**：不新增功能、不改接口，验收标准以"原有交互不变 + 类型检查与构建通过"为限。

**共同原则**：三项动作都不改变对外接口与既有功能，每个改动都附带可复核的测试/构建证据，且由另一名组员 review 后合并——这本身就是可维护性的制度化保证。
